# Adding a stack to this homelab

## Overview

This homelab has one control plane (Komodo) and four ways a stack can reach the
server. Picking the wrong one is not a style error — it produces a stack that
looks healthy and serves nothing, or one that never redeploys. Pick the method
first, then follow that method's checklist.

Read [README.md](../../../README.md) for the architecture this assumes.

## Which method?

Two questions decide it.

| Does this repo own the compose file? | Does the stack need an image built? | Method |
|---|---|---|
| yes | no  | **1. Komodo git Stack** — the default |
| yes | yes | **2. Komodo git Stack + CI build** |
| no (another repo generates it) | either | **3. `file_contents` Stack, driven by that repo** |
| yes, but it must survive a broken control plane | no | **4. Host-managed, never deployed** |

Method 4 is only for the tunnel and Komodo itself. Anything that can be
deployed can be broken by a deploy; the path you would use to repair the server
must sit outside that blast radius. Do not add a fifth member without a reason
of that kind.

## Method 1 — Komodo git Stack

Examples in this repo: `immich`, `home-assistant`, `monitoring`, `registry`.

1. **Repo directory** `<stack>/` holding `docker-compose.yml` and `.env.example`.
   Commit both. Never commit `.env` — the `*/.env` gitignore rule covers it.
2. **Komodo Stack** via `CreateStack`, with `project_name` **exactly** the
   directory name. See `references/komodo-api.md` for the payload.
3. **Host `.env`** at `/etc/komodo/stacks/<stack>/<stack>/.env`, root-owned
   `600`. The checkout only exists after Komodo's first deploy. If starting with
   a wrong/absent `.env` would initialise a database (Postgres, Grafana), clone
   the checkout by hand *first* — an untracked `.env` survives Komodo's pull.
4. **GitHub webhook** on this repo pointing at
   `<KOMODO_URL>/listener/github/stack/<stack>/deploy`, content type
   `application/json`, secret `KOMODO_WEBHOOK_SECRET`.
5. **README** — add a row to the stack table and a line to the repo layout.

If the stack bind-mounts config out of the checkout, also set
`webhook_force_deploy: true`, and add a `post_deploy` restart *only if the
service does not watch its own config*. See **Config mounted from the checkout**
below.

## Method 2 — Komodo git Stack + CI build

Example: `config` (the only one). Everything in Method 1, plus:

6. **Dockerfile** under `<stack>/<image>/`.
7. **`.github/workflows/deploy.yml`** — add a `dorny/paths-filter` entry scoped
   to the image's source only, a `docker/build-push-action` step tagging both
   `:latest` and `:${{ github.sha }}`, and a signed POST to the stack's Komodo
   listener **in the same job, strictly after the build**. Copy the existing
   `config-agent` steps.

The ordering is the whole point: Komodo must never pull an image GHCR does not
have yet. A split across two jobs deploys the previous `:latest` and reports
success.

**Filters are `some` by default.** A negated pattern (`'!path/**'`) matches every
path it does not name, so the filter fires on every commit in the repo. Use a
positive glob instead.

## Method 3 — `file_contents` Stack driven by another repo

Example: `trakt-tg-bot`, whose compose file is generated by .NET Aspire.

1. **Komodo service user + API key**, with Write on that one Stack and nothing
   else. Never hand a foreign CI an admin key.
2. **Komodo Stack** in `file_contents` mode (starts as `services: {}`), with
   `project_name` pinned to the live project name.
3. That repo's CI pushes compose **and** env in one `UpdateStack`, then polls
   `GetUpdate` — `/execute` returning 2xx means *accepted*, not *deployed*.
4. This repo documents only the seam (e.g. monitoring joining its network).

## Method 4 — Host-managed, never deployed

Examples: `tunnel`, `komodo`.

1. Repo directory with `docker-compose.yml` and `.env.example`, as usual.
2. Add it to `STACKS` in [scripts/bootstrap.sh](../../../scripts/bootstrap.sh),
   in dependency order.
3. **Do not** create a Komodo Stack for it, and **do not** add it to
   `deploy.yml`. Say why in a comment at the top of its compose file.

## Rules that apply to every method

- **`project_name` is load-bearing.** Named volumes are `<project>_<volume>`. A
  different project name creates fresh empty volumes and every container starts
  healthy. Pin it to the directory name and never change it.
- **Acceptance is a data assertion, never a health check.** Count rows, list
  the catalog, check the library — "all containers up" proves nothing.
- **Mount directories, never single files.** A bind mount pins an inode and git
  replaces files rather than editing them, so a single-file mount is frozen at
  the version present when the container started.
- **Secrets never enter git.** `.env` on the host only. GitHub Actions holds
  just `KOMODO_URL` and `KOMODO_WEBHOOK_SECRET`.
- **Config mounted from the checkout always needs `webhook_force_deploy:
  true`**, or edits silently do nothing — the default check compares only the
  compose file's contents and ignores everything mounted beside it.
- **It needs a `post_deploy` restart too, *unless the service watches its own
  config*.** `docker compose up` leaves a container alone when its service
  definition has not changed, so most services need the nudge. But Caddy runs
  with `--watch` and reloads in place, and a restart there would recreate the
  proxy and sever the response path the deploy is travelling on — which is the
  whole property the `config` stack is built around. Check whether the service
  self-reloads before adding one. Note that self-reload can be defeated by a
  *single-file* bind mount (the inode trap): mount the directory and it works.

  The two live stacks that mount config are the worked example, verified
  2026-08-25 against Komodo's API:

  | stack | `webhook_force_deploy` | `post_deploy` | why |
  |---|---|---|---|
  | `config` | true | *none* | Caddy runs `--watch` and reloads itself |
  | `monitoring` | true | `docker restart prometheus promtail tempo otel_collector` | none of those four watch their config |

## Common mistakes

| Symptom | Cause |
|---|---|
| Stack healthy, all data missing | `project_name` doesn't match the old one — volumes were created empty |
| Push to `main`, CI green, nothing deploys | `webhook_enabled: true` set, but no GitHub webhook created. It's a door, not a knock |
| Config edit reaches the repo, not the container | Missing `webhook_force_deploy: true`, or a single-file bind mount, or no `post_deploy` restart |
| Deploy lands the previous image and reports success | Build and trigger split across jobs instead of ordered in one |
| Listener answers `200`, no deploy happens | Body had no `ref`, or `webhook_force_deploy: false` and nothing changed. Only a new Update proves a deploy |
| Every push redeploys an unrelated stack | A negated `!pattern` in the paths-filter |
| `curl` exits 3 with no error message | An Actions secret that was never created expands to an empty string |

## Verifying

A Komodo `200` is not evidence. Confirm the deploy moved the Stack's update
count, then assert on data. For the `config` stack specifically, a red CI run is
also not evidence: redeploying it restarts Caddy, which severs the connection
the success response was travelling on.
